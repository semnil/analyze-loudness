# analyze-loudness

A tool that analyzes the audio loudness of YouTube videos in compliance with BS.1770 / EBU R128.
It comes in two forms: a CLI version and a GUI application version (Windows / macOS).

## Documentation languages

- **Override of the global CLAUDE.md's 「ドキュメント」 language rule**: this file is written entirely in English, and the documents are maintained in both English and Japanese — English at `README.md` and `docs/architecture.md`, Japanese at `README.ja.md` and `docs/architecture.ja.md`.

## Architecture overview

The diagram of the processing flow is in the "System Architecture" section of `docs/architecture.md`.

The GUI consists of pywebview (Windows: WebView2 / macOS: WebKit) + a local HTTP server.

## Design decisions

### ebur128 parsing

Parses the stderr of `ffmpeg -af ebur128=peak=true -f null -` with the regex `t:\s*([\d.]+)\s+TARGET.*?M:\s*([-\d.]+)\s+S:\s*([-\d.]+)`. The Summary block takes Integrated / LRA / True Peak from `output.rfind("Summary")` onward.

### Memory constraints

Decoding 50 minutes of audio to WAV takes more than 4 GB and runs out of memory.
No raw decode is done; only the stderr text output of ffmpeg ebur128 is processed.

### Silence thresholds

Statistics use only frames with Short-term > -60 LUFS (`SILENCE_THRESHOLD`). The silence ratio is computed with S < -40 LUFS
(`SILENCE_PCT_THRESHOLD`). However, **ebur128's warm-up frames are left out of the denominator** —
S is a 3-second window, so the first 29 frames do not fill the window and output the silence floor -120.7. Without the exclusion,
a 36-second clip shows 8.1% silence (measured; the actual figure is 0.0%). The decision is centralized in `first_full_window()` / `compute_silence_pct()` of `src/analyze_loudness/analysis.py`
and shared by three places: the CLI, the GUI and the matplotlib plot.

### Middle extraction

Cuts the audio directly during the ebur128 analysis with `ffmpeg -ss`/`-t`, starting at `(total length - extract minutes*60) / 2`. When the source is shorter than the given number of minutes, the full length is used.

This feature is exposed through the CLI's `--duration` option (single analysis only). The GUI does not implement a minutes input UI by policy (it keeps the simple workflow of entering only a URL or a local file path, and always analyzes the full length). The GUI backend's `/analyze` endpoint keeps the validation that accepts a `duration` field, but the frontend never sends it.

### Local files

The input field accepts a URL or a local path. Input that contains `://` or starts with `javascript:` is a URL only when it is http(s);
anything else is treated as a local path (`/analyze` in `src/analyze_loudness/gui.py` on the server, and `_sourceKind` in `frontend/main.js` on the frontend, mirror
the same rule). UNC paths and device paths starting with `\\` or `//`, and NT namespace paths that start with `\??\` once `.` / `..` segments are applied
(`\??\UNC\host\share\...`, `\.\??\...`), are refused before resolving or checking existence
(`is_network_path` in `src/analyze_loudness/download.py`; on the frontend, `"network"` of `_sourceKind`). A local file is made absolute and kept as is in `meta.source_url`, and its title is the
file name without the extension. The file's modification time is added to the cache key, and of the results read by `/load`, those with a local source
are not put in the cache. A dropped file is placed by `/upload` in a temporary directory (deleted on exit), so
the `meta.source_url` of that result is a path in the temporary directory.

### Download format

opus (much smaller than uncompressed WAV). Calls the Python API of `yt_dlp.YoutubeDL` directly and extracts with the `FFmpegExtractAudio` postprocessor. The title is taken from the return value of `extract_info(download=True)`, so there is no need to run title fetching and the download in parallel.

### yt-dlp Python API (not a binary)

Bundling a PyInstaller onefile binary such as `yt-dlp_macos` causes a Team ID mismatch in the internal `Python.framework` at CI's codesign re-signing (macOS hardened runtime). Installing `yt-dlp` as a Python dependency and using the `YoutubeDL` class directly avoids this problem. Windows / Linux use the same approach for consistency.

### yt-dlp version pin

`pyproject.toml` has an exact pin `yt-dlp==<version>`. The three `pyproject.toml` files of analyze-loudness / analyze-spectrum / py-analyze-common have the same pin, and a manual version change updates all three at the same time. In analyze-loudness and analyze-spectrum, a Dependabot update of the Python dependencies (the yt-dlp pin included) is merged automatically at any semver level once its required checks pass, unless someone other than Dependabot pushed a commit to its PR (`.github/workflows/dependabot-auto-merge.yml`), so the three values can differ. In analyze-loudness and analyze-spectrum, Dependabot (`.github/dependabot.yml`, the `uv` ecosystem) opens an update of the pin and of `requirements/*.txt` every day at 00:00 JST, for a version released at least three days before; py-analyze-common's Dependabot does not watch its Python dependencies, so its pin is changed by hand. In analyze-loudness and analyze-spectrum the checks pass only when the update also keeps `requirements/release.txt` in step with `pyproject.toml` ([Pinned release dependencies](#pinned-release-dependencies)). What goes into the shipped app is the pin in this repository's `pyproject.toml`; py-analyze-common's `pyproject.toml` is not used to build the shipped app (the submodule is read through `sys.path` injection).

Why pin: the shipped app has yt-dlp baked into the PYZ by PyInstaller, so it cannot be updated after installation. Leaving it unpinned makes the version depend on the resolution at build time, and the version inside a shipped app cannot be identified afterwards.

Check the pinned version before opening the version bump PR of the [Release procedure](#release-procedure). A pin changed by a Dependabot auto-merge reached master without this check:

1. In a `.venv` with the version pinned in this repository's `pyproject.toml`, confirm a **full-length download**. `--test` (fetches only the first 10 KiB) cannot detect a 403:
   `.venv/bin/python -m yt_dlp -f bestaudio -o <tmpdir>/%(id)s.%(ext)s <URL>`
   Confirm with three kinds: a normal video, a live archive and a Short
2. If it fails, install a candidate version with `pip install -U yt-dlp`, run the same check, and write the version that passes into the three `pyproject.toml` files. Commit py-analyze-common first, then update the submodule pointer. In analyze-loudness and analyze-spectrum, regenerate `requirements/*.txt` in the same commit as the `pyproject.toml` change ([Pinned release dependencies](#pinned-release-dependencies))

### macOS is Apple Silicon (arm64) only (v1.3.0+)

ffmpeg / ffprobe are fetched as osxexperts.net's arm64 native builds. evermeet.cx (x86_64) is not used because (a) an Intel Mach-O in the bundle makes macOS 26 show the warning that support for apps for Intel processors is ending, and (b) connections from the GitHub Actions macos runner time out. Intel Mac support ended with v1.2.0.

### Bundled ffmpeg pin

`build_assets/ffmpeg.json` holds the series (`series`, e.g. `8.1`) of the ffmpeg / ffprobe bundled on both OSes, and the URL and SHA256 of the macOS build. Reading, writing and validation are done by `analyze_common/ffmpeg_release.py` of py-analyze-common, which `build.py` calls.

- macOS: `build.py` fetches the osxexperts.net zip and checks the binaries in it against the pinned SHA256 (a mismatch stops the build). This SHA256 is the same value the osxexperts.net page shows next to the download
- Windows: the build of the same series in `latest` of BtbN/FFmpeg-Builds (`ffmpeg-n{series}-latest-win64-gpl-{series}.zip`; the lgpl builds are not used). Its contents change daily, so the SHA256 is not pinned. When the series disappears from `latest`, the build stops
- Updates: `.github/workflows/ffmpeg-watch.yml` does this daily and carries it through to a patch release ("Patch release for an ffmpeg update" in the [Release procedure](#release-procedure)). The osxexperts.net URL is not derived from the version (`ffmpeg81arm.zip` / `ffmpeg9arm.zip`), so the pin is taken from the page's links. To do it by hand, the following command — only when the page has a different build — confirms that BtbN has the same series and that both files match the page's SHA256, then writes the new pin to `--candidate`. When `pin_update=true`, copy its contents to `build_assets/ffmpeg.json`

  ```bash
  PYTHONPATH=vendor/py-analyze-common/src .venv/bin/python -m analyze_common.ffmpeg_release detect \
    --pin build_assets/ffmpeg.json --version-file src/analyze_loudness/__init__.py --candidate <tmpdir>/ffmpeg.json
  ```

- Verification: `tests/test_ffmpeg_binary.py` reads a 1 kHz sine wave written with numpy through the ffmpeg / ffprobe on PATH and the app's parsers (`run_ebur128()` / `probe_duration()`), and compares Integrated, the relative gate and True Peak with the BS.1770 calculation. Given the directory of the bundled binaries in `EXPECT_FFMPEG_DIR`, it confirms the ffmpeg / ffprobe there are found first, and fails instead of skipping when they are not (the last line of [Tests](#tests)). The release build (`.github/workflows/release.yaml`) runs this test on the copies inside the distributables (on Windows `dist/analyze-loudness/_internal/bin` collected by PyInstaller, on macOS `Contents/Frameworks/bin` of the `.app` after signing), and on failure it does not proceed to uploading the artifacts and creating the Draft Release (`tests/test_release_workflow.py` checks the position of that step and the directory it passes against the spec and `installer.iss`)

### Starting ffmpeg / ffprobe by absolute path

`run_ebur128()` in `src/analyze_loudness/analysis.py`, and py-analyze-common's `probe_info()` / `download_audio()`, start ffmpeg / ffprobe (and yt-dlp's deno) by the absolute path that py-analyze-common's `find_executable()` returns. It searches only the absolute entries of PATH, in order; the frozen app puts the bundled `bin` folder at the front of PATH (`main()` in `src/analyze_loudness/gui.py`). The reason is in the "Programs start by absolute path" section of `vendor/py-analyze-common/CLAUDE.md`. When the program they run is not on PATH (ffmpeg for `run_ebur128()` / `download_audio()`, ffprobe for `probe_info()`), they raise `FileNotFoundError` without starting a process. `tests/test_ffmpeg_binary.py` checks `EXPECT_FFMPEG_DIR` with the same `find_executable()`.

### deno (yt-dlp dependency)

yt-dlp needs the deno runtime for YouTube's JavaScript extraction. `build.py` downloads the latest version and bundles it. The challenge solver scripts yt-dlp runs on it come from `yt-dlp-ejs` (GUI dependencies).

### Local HTTP server + pywebview

Starts an HTTPServer on a random port of 127.0.0.1 (port 0). Shows the window with pywebview (Windows: WebView2 / macOS: WebKit).
Shows real-time progress with NDJSON streaming. Estimates the remaining time with `_speed_factor`, calibrated at run time.

### Dark mode

Three-state theme switching light / dark / auto with CSS variables + `[data-theme="dark"]`.
CSS variable names are shared with analyze-spectrum (`--text` / `--bg-card` / `--text-secondary` / `--text-muted` etc.). The CSS variables and rules that are the same in both apps live in py-analyze-common's `analyze_common/web/common.css`, which `src/analyze_loudness/gui.py` serves as `/common/common.css` (the PyInstaller spec bundles it in `analyze_common/web`). `frontend/index.html` loads it before `frontend/style.css`, and `frontend/style.css` holds the remaining variables (accent color etc.) and its own rules. The `h1` of the narrow-screen `@media (max-width: 480px)` has to come after the `h1` of each `style.css`, so it stays in `style.css`.
The default is `auto` (follows the OS `prefers-color-scheme`). The choice is saved with `/settings` to `theme` in the app's settings file (the same `settings.json` as "Settings" in the "Auto-update" section). The page starts drawing with `window.analyzeSettings.theme` passed by `/common/settings.js` (py-analyze-common's `UiSettings.script()`; `Cache-Control: no-store`), `main()` decides the window's background color with `UiSettings.background_color()`, and `analyze_common.ui_settings.show_window_color_until_paint()` right after `create_window()` shows that color on macOS until the page is drawn (pywebview attaches WKWebView to the window only after the first load finishes, and WKWebView draws white until its first paint, so its background is turned off; the mechanism is in the "Theme and language settings" section of `vendor/py-analyze-common/CLAUDE.md`). When saving fails, the chosen theme stays and the status area shows an error.
The theme toggle UI is a pill button fixed at the top right (SVG of a sun / crescent moon / half-filled circle, generated by `_createThemeIcon()`). Unified with analyze-spectrum.
Chart colors are managed in one place by `getTheme()` of `frontend/theme.js`, and the charts are redrawn on a theme switch.

### i18n (languages)

`frontend/i18n.js` manages two languages, en / ja. However, the display items of tables and charts (table.*, chart.*, summary.frames/min etc.) are English-only, unified with analyze-spectrum. The ja dictionary also has the English values for these keys. The UI chrome such as buttons, status and error messages keeps its Japanese translation.
The chosen language is saved with `/settings` to `lang` in the same settings file as the theme, and passed to the next page through `window.analyzeSettings.lang`. When nothing is saved, it follows `navigator.language` (`ja*` is ja, anything else en).
Elements whose text `main.js` writes according to state (the theme button's `aria-label`, the submit button's text and `aria-label`) do not get `data-i18n*`; `main.js` writes them on load and on `window.i18n.onChange` (with the attributes, DOMContentLoaded and every language switch would reset them to a fixed text).

### Chart titles drawn once (unified with analyze-spectrum)

The title of each chart (timeline / histogram x2 / segments) is drawn only as an HTML `<h3 class="chart-title">`; Canvas / uPlot `ctx.fillText` and the `title:` option are not used. Drawing inside the canvas is forbidden because it leads to a double display and a duplicate in the PNG export (`captureImage()` burns the titles into the composite PNG with the `label` of each element `{canvas, label}` of `chartCanvasRefs`). The HTML titles have tooltips (`tip.chart_timeline` / `tip.chart_histogram` / `tip.chart_segments`) through `_addTip()`.

`role="img"` + `aria-label` go on the canvas itself for the histograms, and on the container div for timeline / segments. The title is always placed outside that node (ARIA treats the descendants of `role="img"` as presentational, so inside it the title and the tooltip text do not reach assistive technology).

### GATE lane (excluded blocks on the timeline)

Integrated aggregates only the 400 ms blocks that pass BS.1770's absolute gate (-70 LUFS) and relative gate (the mean of the blocks that passed the absolute gate -10 LU).
A 12 px high band is placed in the timeline's x-axis gutter (between the bottom of the plot and the tick labels), showing excluded blocks in amber (at or below the relative gate) / slate (at or below the absolute gate).

ffmpeg outputs a frame every 100 ms, but the Momentary window is 400 ms, so **the first 3 frames
(t = 0.1 / 0.2 / 0.3) do not fill the window and output the silence floor -120.7**. They are not gating blocks,
so `computeGate` decides the start from `series.t` and excludes them (`_firstGatedIndex`). Without the exclusion,
both the silence ratio and the denominator grow (the measurements are in the "GATE lane" section of `docs/architecture.md`).
The decision is relative to `t[0]`, so it also works when cut with `-ss`. The warm-up of S (3-second window) is 29 frames, and
the summary's silence ratio excludes those with the same rule ([Silence thresholds](#silence-thresholds)).

The relative gate value comes from `summary.gate_threshold` (schema 2); only when it is missing does `computeGate()` of `frontend/gate.js`
recompute it from `series.M`. JSON saved with schema 1 takes this fallback path.
The agreement between the recomputed Integrated and the saved value is measured in the "GATE lane" section of `docs/architecture.md`.
The band appears with either path. For a JSON whose `series.M` length differs from `series.t`, the band is not shown
(the correspondence with the time axis cannot be guaranteed).

The ffmpeg Summary has **two** `Threshold:` lines (the Integrated one and the LRA one).
The regex in `src/analyze_loudness/analysis.py` anchors on the `I:` line and takes the former. The latter is something else.

The values ffmpeg outputs are rounded to 1 decimal place, so the results of the two paths do not match exactly. Rounding changes the decision
only for blocks that sit exactly on the threshold (the measured counts are in the "GATE lane" section of `docs/architecture.md`).
The 1-decimal side reproduced ffmpeg's Integrated more faithfully in 12 of 13 saved JSON files.

### JSON schema version

`SCHEMA_VERSION` is in `src/analyze_loudness/__init__.py`. It is raised independently of `__version__` (the app version).

| ver | Added |
|-----|------|
| 1 | Initial version |
| 2 | `summary.gate_threshold` — ffmpeg's relative gate. When missing, the frontend recomputes it from `series.M`. At the same time `summary.silence_pct` started leaving ebur128's warm-up frames out of the denominator (values already saved with schema 1 keep the old computation) |
| 3 | Comparison JSON (`compare.tracks`). The contents of a single result are the same as schema 2 |

`/load` only validates that `meta.schema_version` is an int and does not reject by its value. Single or comparison is branched on the presence of `compare`.
New fields **branch on their presence, not on the version number** — a hand-edited JSON may lack them.

The band's space is made by widening the x axis's `gap` / `size` and the chart height by the same 11 px each. The plot bbox does not change
with or without the band (measured in the "GATE lane" section of `docs/architecture.md`). When a pixel column mixes included and excluded blocks, it is drawn as excluded, so
on long recordings the band's filled area exceeds the actual exclusion ratio. Drag-zooming converges on the actual excluded ranges.

The colors are defined in two places: `gateTrack` / `gateOut` / `gateSilent` in `frontend/theme.js` and the CSS variables
`--gate-track` / `--gate-out` / `--gate-silent` (for the canvas and for the legend chips).
Changing only one makes the legend and band colors drift apart.

### Comparison mode

Overlays 2-6 results from the start and truncates all tracks to the length of the shortest track. The statistics of the truncated range are
computed only by `truncated_stats()` in `src/analyze_loudness/compare.py`; the frontend shows the `stats` returned by `/compare` and `/load`.
The Integrated and the GATE band of the truncated range recompute the relative gate (they do not use the full-length `summary.gate_threshold`).
The verification measurements, the shape of the comparison JSON and the reasons for the track colors are in the "Comparison mode" section of `docs/architecture.md`.
`MIN_TRACKS` / `MAX_TRACKS` are mirrored between `src/analyze_loudness/compare.py` and `frontend/main.js`, the gate constants
(`GATE_ABSOLUTE` / `GATE_RELATIVE_OFFSET` / `GATE_BLOCK_SEC`) between `src/analyze_loudness/compare.py` and `frontend/gate.js`,
and the track colors (light) between `trackColors` in `frontend/theme.js` and `TRACK_COLORS` in `src/analyze_loudness/plot.py`; always update them together.

### Auto-update

The installed version (the Windows / macOS app built with PyInstaller) checks GitHub's latest Release at launch, and when there is a newer version it shows a confirmation dialog (`window.confirm`, OK / Cancel). Only on OK does it fetch, verify and apply the installer and restart the app. The core lives in py-analyze-common's `analyze_common/update.py` (check, fetch, signature verification, apply) and `analyze_common/web/update.js` (gear button, settings dialog, confirmation flow), shared with analyze-spectrum. This repository holds `UPDATE_CONFIG` in `src/analyze_loudness/update.py` and the three `/update/*` endpoints in `src/analyze_loudness/gui.py`.

- Settings: the settings dialog opened by the toolbar's gear button has "Check at launch" (default ON), "Check now" (the result is shown inside the dialog) and the version. "Check at launch" is saved with `/update/settings` to `update_check_at_launch` in the app's settings file (macOS `~/Library/Application Support/analyze-loudness/settings.json`, Windows `%APPDATA%\analyze-loudness\settings.json`) and returned by `/update/status`. It is not kept in the webview's localStorage (pywebview starts in private mode, and the local server's port = origin changes on every launch, so localStorage does not survive to the next launch). While a save request is in flight the toggle is disabled (requests do not overlap), and after saving it is redrawn with the value the server returned. When saving fails it goes back to the value before the save and says so inside the dialog. The check at launch shows nothing when the app is up to date or the check fails. When the check at launch and "Check now" overlap, they are merged into one check
- Builds that can apply updates: frozen Windows x64 and macOS arm64 (`supported` of `/update/status`). When run in development, the update row of the settings dialog is disabled
- During an analysis it declines without showing the confirmation dialog ("Check now" says so inside the dialog). During the download, analysis and the settings dialog are blocked
- Verification: `latest.json` on the Release holds each OS's installer URL and Ed25519 signature. The signed statement is `analyze-update-v1` / product name / version / OS / the installer's SHA-256 joined by newlines, verified with `PUBLIC_KEY` of `UPDATE_CONFIG`. Because the version and OS are in the signature, swapping in an old legitimate installer with a newer version number, or reusing a file for another OS, fails verification. Only URLs under `https://github.com/semnil/analyze-loudness/releases/download/` are accepted, and only redirects that stay on https are followed. The CA is certifi
- Windows: starts the verified `LoudnessAnalyzer-X.Y.Z-setup.exe` with `/SILENT /SUPPRESSMSGBOXES /NORESTART /CLOSEAPPLICATIONS /UPDATE=1` through `os.startfile` (the installer shows UAC; Inno Setup's loader starts `asInvoker` and asks for elevation only when it needs it), and the app closes its window and ends normally. `vendor/py-analyze-common/installer/auto_update.iss`, included by `installer.iss`, waits only when `/UPDATE=1` until the app's mutex is gone, installs, and when done starts the app with the original user's rights. If the mutex is still there after 30 seconds, it shows Inno Setup's "is running" message; OK waits again and Cancel ends without installing. The app ends when it starts the installer, so declining UAC leaves the update not installed and the app closed (launching it again starts the old version, and with the check at launch ON it offers the same update again). The mutex name is held only by `UPDATE_CONFIG.mutex_name`; `main()` holds it with `hold_instance_mutex()`, and `build.py` passes it to Inno Setup with `/DMyAppMutex=` (`installer.iss` has `#error` when it is undefined)
- macOS: opens the DMG, copies the `.app` to a temporary directory on the same volume, checks the identifier and version, and — when the current version is signed with a Team ID — the same Team ID and `codesign --verify --deep --strict`, then swaps it with the running `.app` (`RENAME_SWAP` of `renamex_np`; asks for the administrator password when it lacks permission). After the swap the bundle on disk is the new version, so `_exit_now()` runs the atexit cleanup itself and ends with `os._exit(0)`. The restart is done by a shell that waits for this process to end and then runs `open`. It does not swap while another process of the same executable is running, or when started from inside the DMG or from App Translocation
- Failure: failures other than the check are shown as an error in the status area, and the app keeps running

The signing key is Ed25519. The private key is not put in the repository; the contents of the PEM are registered as the repository secret `UPDATE_SIGNING_KEY`. The public key (base64 of the raw 32 bytes) is written to `PUBLIC_KEY` in `src/analyze_loudness/update.py`. Creating the key needs OpenSSL 3 or later (the LibreSSL 3.3 bundled with macOS cannot create Ed25519 keys; use Homebrew's `openssl@3`).

```bash
openssl genpkey -algorithm ed25519 -out analyze-loudness.pem
PYTHONPATH=vendor/py-analyze-common/src python -m analyze_common.update_manifest public-key analyze-loudness.pem
gh secret set UPDATE_SIGNING_KEY < analyze-loudness.pem
```

The sign-manifest job of `.github/workflows/release.yaml` makes `latest.json` with `python -m analyze_common.update_manifest sign`, and the create-release job puts it on the Release together with the installers. `UPDATE_SIGNING_KEY` is referenced only by sign-manifest, which runs with a read-only token, a checkout without stored credentials and no pip cache, and installs only the `yt-dlp` wheel in `requirements/sign-manifest.txt` (`--require-hashes --no-deps --only-binary :all:`; `analyze_common` imports `yt_dlp`). create-release is the only job with `contents: write`, and it runs no Python (`tests/test_release_workflow.py` checks both). The sign-manifest job fails when the secret is missing, when the created signature cannot be verified with `PUBLIC_KEY` (the secret and the public key disagree), or when the tag is not `v` + `__version__`.

### Window icon

PyInstaller's `EXE(icon=...)` is only the icon of the EXE file itself (shown in Explorer). The pywebview window icon (title bar and taskbar) needs an explicit `webview.start(icon=...)` (moved from `create_window` to `start` in pywebview 6.x). `build_assets/icon.ico` is bundled through PyInstaller's `datas` and resolved through `_ICON_PATH`.

The `icon=` argument is passed only on Windows (`sys.platform == "win32"`). On macOS the Dock/app icon comes from the `.app` bundle (`CFBundleIconFile` = `icon.icns`); passing `icon=` there makes pywebview's Cocoa backend call `NSApplication.setApplicationIconImage_`, which overrides the bundle icon with the raw `icon.ico` bitmap. That bitmap carries no icon-grid inset, so on macOS 26 the Dock renders it edge-to-edge (oversized) instead of at the system-masked size the bundle icon gets.

The Windows taskbar groups processes by AppUserModelID. When it is not set, the Python runtime's default ID is used and the icon embedded in the EXE does not show on the taskbar. `_set_application_user_model_id()` sets `com.semnil.loudness-analyzer` so the taskbar icon shows correctly.

### Windows subprocess console hiding

In PyInstaller frozen mode, `STARTF_USESHOWWINDOW` hides the console window of the ffmpeg / ffprobe the app starts. yt-dlp runs as a Python API, and its own `Popen` (`yt_dlp/utils/_utils.py`) sets `STARTF_USESHOWWINDOW` on Windows for the ffmpeg / ffprobe / deno it starts.

## Release procedure

Before opening the version bump PR, check the pinned yt-dlp version with a full-length download ([yt-dlp version pin](#yt-dlp-version-pin)).

1. Open a PR that raises `__version__` in `src/analyze_loudness/__init__.py` (a version bump contains no other change)
2. After the merge, when the CI run of the push to master succeeds, `.github/workflows/tag-release.yml` detects the change of `__version__`, puts a `vX.Y.Z` tag on the merge commit, and starts `.github/workflows/release.yaml` with `workflow_dispatch` on that tag
3. `.github/workflows/release.yaml` builds the Windows installer (`LoudnessAnalyzer-X.Y.Z-setup.exe`) and the macOS DMG (`Loudness-Analyzer.dmg`) and creates the Release (`draft: true`) together with the signed `latest.json` ([Auto-update](#auto-update)). Before uploading the artifacts, the build runs the ffmpeg / ffprobe inside the distributables through `tests/test_ffmpeg_binary.py` ("Verification" in [Bundled ffmpeg pin](#bundled-ffmpeg-pin))
4. A person publishes the Release. The published Release becomes `releases/latest`, and the update check of installed apps reads its `latest.json`

The merge of the version bump PR is the starting point of a release. `tag-release.yml` does nothing on a push that does not change `__version__`, and does not move a tag of the same name that already exists on another commit. `tag-release.yml`'s `workflow_dispatch` handles the commit of the input `sha`, and tags it only when it is on master and CI succeeded on that commit or on a parent commit with the same tree (the head of a PR merged with the tip of master included). `release.yaml` also builds and releases on a tag push and on a `workflow_dispatch` on a tag (a `workflow_dispatch` on a branch only builds).

### Pinned release dependencies

The release jobs install nothing that is resolved at build time:

- Python packages: `requirements/release.txt` (the dependencies of `pyproject.toml` and its `gui` and `dev` extras), installed with `--require-hashes --no-deps --no-build-isolation` after `requirements/release-build.txt` (the pip that installs it, and the build backends of its source distributions and of this project). The `sign-manifest` job installs only `requirements/sign-manifest.txt` (yt-dlp, which analyze_common imports) as a wheel
- Build tools: Inno Setup (Windows) and create-dmg (macOS) are downloaded from their GitHub releases and checked against the SHA256 in `release.yaml` (`INNOSETUP_SHA256`, `CREATE_DMG_SHA256`)
- Not pinned: deno and the Windows ffmpeg / ffprobe, which `build.py` downloads ([Bundled ffmpeg pin](#bundled-ffmpeg-pin))

`requirements/*.txt` are generated by uv from `pyproject.toml` and `requirements/*.in` (uv is in the `dev` extra of `pyproject.toml`). Run the following from the repository root after changing the dependencies of `pyproject.toml` (the yt-dlp pin included); add `--upgrade` to the first command to take newer versions:

```bash
uv pip compile pyproject.toml --extra gui --extra dev --universal --python-version 3.12 --generate-hashes -o requirements/release.txt
uv pip compile requirements/release-build.in -c requirements/release.txt --universal --python-version 3.12 --generate-hashes -o requirements/release-build.txt
uv pip compile requirements/sign-manifest.in -c requirements/release.txt --universal --python-version 3.12 --generate-hashes -o requirements/sign-manifest.txt
```

`--python-version` is the `python-version` of `release.yaml`. `tests/test_release_workflow.py` fails when `requirements/release.txt` does not satisfy `pyproject.toml`, when a file was generated with other options, or when uv finds no resolution for the command in a file's header with that file's own pins as constraints (a pin that breaks the requirement of another package in the file), so a branch that changes `pyproject.toml` without regenerating these files does not pass CI, whoever opened it.

### Patch release for an ffmpeg update

`.github/workflows/ffmpeg-watch.yml` does the following daily (and on `workflow_dispatch`), with no human step until the Draft Release is created. The bot merges the PRs without review.

1. detect: compares `build_assets/ffmpeg.json` with the osxexperts.net page ([Bundled ffmpeg pin](#bundled-ffmpeg-pin)). When the page has a different build, it confirms that BtbN has the same series and checks the SHA256 of both files, and makes a new pin. It makes a patch release when `__version__` equals the latest `vX.Y.Z` tag and either the pin changes this time or the current pin differs from the pin that tag released (the pin file in the tag, or, when the tag has none, the pin from when the file was first added after the tag)
2. smoke: on macOS and Windows runners, runs `tests/test_ffmpeg_binary.py` on the pinned binaries fetched with `build.py --ffmpeg-only`
3. land: opens in order the pin PR (`ffmpeg-watch/pin-<series>-<run id>-<attempt>`) and the bump-only PR (`ffmpeg-watch/bump-v<version>-<run id>-<attempt>`, `chore: update the version to vX.Y.Z`), pushing, opening and merging them with the GitHub App's token (the prerequisite below) and reading the PRs and runs with GITHUB_TOKEN. Each PR starts its CI (`Test 🧪`) and `dependabot-auto-merge.yml` (`auto-merge`) runs of `pull_request` and its `workflow-checks.yml` (`action-pins`) run of `pull_request_target`; land merges the PR after the three runs on its head commit succeed and `gh pr checks --required` passes. The merge of the bump runs the CI of the push to master, which starts `tag-release.yml` (step 2 of the [Release procedure](#release-procedure)). GITHUB_TOKEN is not used for these PRs: a PR it opens starts no `pull_request_target` run and its `pull_request` runs wait for an approval, and the checks of runs started with `workflow_dispatch` are not counted as the required checks of master's ruleset (the merge of such a PR was refused with `3 of 3 required status checks are expected.`)
4. A person publishes the Release (step 4 of the [Release procedure](#release-procedure))

- Prerequisite: a GitHub App installed on this repository with the repository permissions Contents (read and write) and Pull requests (read and write), its client ID in the repository variable `FFMPEG_WATCH_APP_CLIENT_ID`, and its private key (the contents of the `.pem`) in the repository secret `FFMPEG_WATCH_APP_PRIVATE_KEY`. The token land creates carries only those two permissions. Without the variable or the secret, land fails at its first step
- When a PR from an earlier run (an open PR whose head is `ffmpeg-watch/`) remains, land fails without changing anything. Close or merge that PR, then run again. The branch name differs per run (run id and attempt), so a branch pushed by a run that failed before opening its PR does not collide with the next run's push (that branch stays without a PR). When only the pin PR was merged and the bump remains, the next run's detect resumes from the bump, as "the current pin differs from the pin the latest tag released". When the bump was merged but there is no tag (for example, the CI run of that push failed), the next run's detect reports the master commit that set `__version__` to that value (`release_sha`), and land passes that commit and starts `tag-release.yml`. If the tag already exists, it does nothing
- When smoke, or any of the runs of a PR (CI, auto-merge, action-pins), fails, or a run does not start within three minutes, land stops at that point and does not merge

## Versioning

The only source of the version is `__version__` in `src/analyze_loudness/__init__.py`. Every other file gets it dynamically from there:

| File | How it gets the version |
|----------|----------|
| `pyproject.toml` | `[tool.hatch.version]` `path` (regex extraction, no import) |
| `analyze-loudness.spec` | read with a regex in `_read_version()` |
| `installer.iss` | injected with `/DMyAppVersion=` by `_build_inno()` in `build.py` |

A version bump changes only `__version__` in `src/analyze_loudness/__init__.py`.
